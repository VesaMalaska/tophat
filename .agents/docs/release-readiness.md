# TopHat 1.0 release readiness

The private `tophat-vault-tests` package is a test harness. The reusable vault is unconfigured and is not an npm application or CLI release.

1. Run all 18 fixture groups and map all 30 approved criteria to evidence.
2. Complete the authorized host project integration: approved package before planning; traceable bounded tasks; derived guidance/route; applicable pnpm validation, independent security/QA; Development Phase synchronization; final project-doc verification and public/private review.
3. Generate the immutable external dossier at the exact resulting TopHat and host candidates. Resolve failed tests, stale evidence and independent review findings. Fixture counts alone do not establish acceptance.
4. Present concrete release metadata/artifacts and limitations to Vesku for separate release-preparation approval. Agree the vault version/tag and metadata location; do not automatically version the private harness.
5. Apply only approved preparation changes, then rerun/rebind candidate evidence and obtain independent review.
6. A Slice 9 implementation PR targets `development`. Independent implementation review and a separate human APPROVED are required for merge. Live host testing is a subsequent, separately managed activity; its absence does not prevent the reviewed implementation merge, but release validation stays pending.
7. Main integration, a tag and GitHub release publication require separately scoped authorization and current-candidate Git safety/evidence checks. Verify the actual integrated commit after any merge; earlier commit evidence does not test the resulting merge identity.

Keep v0.8.0 intact as the historical baseline. No release action is performed by the acceptance helper.

## Deliberate migration from v0.8.0

Work in an explicitly permitted branch. Read-only discovery identifies the actual framework, existing configuration, public documents, tracked/private ownership, current Git state and host validation baseline. Do not treat a legacy routingMatrix or loose PRD as a valid 1.0 contract.

Use `/workspace-attach` and its assessment/finalization workflow. Propose a canonical 1.0 configuration in memory and a package-v1 adaptation of product authority. If requirements are incomplete, use the separate definition/review/finalization stages and genuine human approval. Preserve existing public docs and host configuration until the reviewed exact installation plan is authorized.

A failing baseline produces BASELINE_REQUIRES_DECISION. Do not weaken gates or invent scoped validation. Resolve a bounded prerequisite or obtain an explicit policy revision, then run a fresh passing assessment.

Tracked/shared installation commits only reviewed exact owned paths. Local/private installation appends the approved block to `.git/info/exclude`, preserving existing rules; this does not untrack files. Hook/exclude metadata changes use the same Git integration preflight. The native hook is explicitly installed; no physical Antigravity IDE interception is claimed.

Manual detachment uses read-only inspection and an exact ownership/removal plan. Mixed ownership blocks removal. A separately authorized orchestrator applies the plan and verifies preservation of product files and history. No TopHat CLI, recursive deletion, or automatic Git history rewrite is required.
